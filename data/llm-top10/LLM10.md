## Description

Improper Output Handling refers specifically to insufficient validation, sanitization, and handling of the outputs generated by large language models **before they are passed downstream** to other components and systems. Since LLM-generated content can be controlled by prompt input, this behavior is similar to providing users indirect access to additional functionality.

Improper Output Handling concerns *unsafe use* of model output; [LLM07 Misinformation](LLM07.md) concerns output that is *incorrect or misleading*. Validation and sanitization of model **inputs** is covered by [LLM01](LLM01.md).

Successful exploitation can result in XSS and CSRF in web browsers, and SSRF, privilege escalation, or remote code execution on backend systems.

### Conditions that increase impact

- Excessive application privileges granted to the LLM, enabling privilege escalation or RCE
- Susceptibility to indirect prompt injection granting an attacker privileged access to a target user's environment
- Unvalidated inputs from third-party tools
- Missing context-specific output encoding (HTML, JavaScript, SQL)
- Insufficient monitoring and logging of LLM outputs
- Missing rate limiting or anomaly detection
- **Terminal, log, or IDE sinks that render model output without neutralizing control characters such as ANSI escape sequences**
- **Client renderers (browser, chat UI, IDE, terminal) that automatically fetch external resources referenced in model output** (Markdown images, link previews, iframes), enabling exfiltration of context data through outbound requests

## Potential Impacts

- Remote code execution on backend systems
- XSS and CSRF against users of the application
- Data destruction through generated destructive SQL
- Conversation and context exfiltration via outbound requests from the renderer
- Visual spoofing and clipboard hijacking in terminal sinks

## Common Examples of Risk

1. LLM output entered directly into a system shell or `exec`/`eval`, resulting in remote code execution.
2. JavaScript or Markdown generated by the LLM and interpreted by the browser, resulting in XSS.
3. LLM-generated SQL executed without parameterization, leading to SQL injection.
4. LLM output used to construct file paths without sanitization, resulting in path traversal.
5. LLM-generated content used in email templates without escaping, leading to phishing.
6. **LLM output containing ANSI escape sequences or other control characters written to a terminal, log viewer, or IDE pane that interprets them** — enabling visual spoofing, clipboard hijacking (OSC 52), or exploitation of known terminal emulator vulnerabilities.
7. **The chat UI auto-renders Markdown images or link previews referenced in model output**, allowing an attacker who controls part of the model context to exfiltrate conversation data via the image URL's hostname or query string.

## Prevention and Mitigation

| # | Strategy | Description |
|---|----------|-------------|
| 1 | Treat the model as any other user | Zero-trust approach; apply proper input validation on responses coming from the model to backend functions. |
| 2 | Follow OWASP ASVS | Use ASVS guidance for effective input validation and sanitization. |
| 3 | Encode model output back to users | Mitigate undesired code execution by JavaScript or Markdown; ASVS provides output-encoding guidance. |
| 4 | Context-aware output encoding | Based on where the output is used — HTML encoding for web content, JavaScript encoding for browser script contexts. |
| 5 | Parameterized queries | Use prepared statements for all database operations involving LLM output. |
| 6 | Strict Content Security Policy | Mitigate XSS from LLM-generated content. |
| 7 | Logging and monitoring | Detect unusual patterns in LLM outputs that might indicate exploitation attempts. |
| 8 | Sanitize control characters | Strip ANSI escape sequences, BEL, OSC, backspace, and carriage return from output before it reaches terminals, log files, or other interpreting sinks. Encode them visibly where they must be preserved. |
| 9 | Prevent renderer-triggered outbound requests | In chat UIs, IDEs, email clients, and mobile apps, **disable auto-rendering of Markdown images, link previews, and iframes by default**. Where rendering is required, restrict fetches to an explicit origin allowlist or proxy them through a server-side fetcher that strips data-bearing query parameters. |

## Example Attack Scenarios

1. A general-purpose LLM passes its response without output validation to a tool that also offers administrative functions, causing the tool to shut down for maintenance.
2. A website-summarizer tool processes a page containing a prompt injection instructing the LLM to capture sensitive content and send it, without output validation or filtering, to an attacker-controlled server.
3. An LLM crafts SQL queries for a backend database through a chat feature. An unscrutinized query to delete all tables is executed.
4. A web app generates content from user prompts without output sanitization; a crafted prompt returns an unsanitized JavaScript payload, leading to XSS when rendered.
5. An LLM generates dynamic email templates; an attacker manipulates it to include malicious JavaScript, leading to XSS for recipients using vulnerable email clients.
6. An application automatically compiles and deploys LLM-generated code without human review or security testing, so insecure code reaches production and is exploited.

## AISVS Controls

| AISVS Section | Control | Key Requirements |
|---------------|---------|-----------------|
| C7.1 Output Format Enforcement | Schema validation with rejection on mismatch; length limits and termination controls | 7.1.1, 7.1.2 |
| C7.3 Output Safety | Harmful-content blocking, system-prompt/backend disclosure filtering, **prevention of model-triggered outbound requests**, **detection of hidden or encoded content via homoglyphs, formatting, metadata, or structured fields** | 7.3.1–7.3.4 |
| C9.2 High-Impact Action Approval | Approval gate before acting on output; reversibility classification and enforcement | 9.2.1, 9.2.3, 9.2.4 |
| C9.3 Component Isolation and Tool Authorization | Least-privilege tool sandbox, **tool outputs validated against schemas**, architectural separation between untrusted tool output and agent operations | 9.3.1, 9.3.2, 9.3.6 |
| C9.5 Agent Authorization & Delegation | Runtime-enforced authorization of tools and parameter values; access decisions never made by the model | 9.5.1, 9.5.3 |
| C10.4 Schema, Message, and Input Validation | Validate MCP responses against declared schemas; reject unrecognized or oversized parameters; strict schema validation | 10.4.1, 10.4.3, 10.4.4 |
| C12.1 Request & Response Logging | Log AI interactions with session context and AI-specific telemetry | 12.1.1 |
| C12.2 Detection and Alerting | Behavioral anomaly detection on output patterns indicating exploitation | 12.2.2 |
